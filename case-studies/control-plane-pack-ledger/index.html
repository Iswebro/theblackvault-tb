Engineering & governance case study

Control Plane andGit Pack Ledger.

How Black Vault Nexus designed the removal of a single point of failure from its multi-model AI operations: a dual-surface control-plane contract, append-only Git evidence ledgers, a fail-closed activation lifecycle, an independent reviewer gate and a human operator holding final authority — landed as a documentation and governance implementation, independently audited, and deliberately not switched on until each future gate is separately approved.

The problem

One connector held the keys.

Black Vault Nexus is built with a multi-model AI workflow: several AI executors do scoped work, and a human operator holds every meaningful decision. The instructions those executors must read first — the canonical “control plane” — lived in exactly one place: Microsoft OneDrive, reached through one cloud connector.

That made the connector a single point of failure, and the failure mode is real, not hypothetical: the repository’s own workflow records note repeated Microsoft 365 connector attach failures forcing blocked or degraded runs. When the connector was down, an executor could not even read its own instructions — and in a workflow where safety comes from executors refusing to act without verified instructions, “can’t read the controls” means “can’t work at all.” The engineering question was how to add a second, Git-based way to recover continuity without weakening a single authorization gate, leaking a single sensitive byte into Git, or letting any automated system promote itself.

What was designed and landed

Six pieces, one discipline: fail closed.

PR #669 landed the governing contracts as documentation. Each piece is fully specified; none of the future-facing machinery is switched on.

Contract

Dual-surface control plane

OneDrive stays the primary — and today the sole operational — canonical surface. A new 2,148-line contract specifies a future read-only Git “recovery projection” on a dedicated ref, so a lane whose connector dies can regain bounded, read-only continuity instead of being fully blocked.

Evidence

Git report ledger

A dedicated, never-merged Git ref (nexus/report-ledger) stores executor final reports as append-only, collision-checked files. Reports become durable, independently fetchable audit artifacts instead of chat messages that disappear — corrections supersede rather than rewrite, and a report is always a claim, never an approval.

Evidence

Side Quest pack ledger

Parallel sandbox work produces “completion packs”: proposed changes plus declared base commit, changed files, validation results and risk notes. A second append-only, never-merged ref (nexus/sidequest-pack-ledger) stores those packs immutably. A pack changes nothing by existing — importing it still requires the normal human-gated PR path.

Future

Recovery projection (PROPOSED)

The projection never stores instruction bytes or prompt bodies. It stores a sanitized, non-executable continuity receipt whose manifest binds each canonical file by SHA-256 hash, byte size and URL. Consumers re-fetch twice, require byte-identical results and a READY status, and fail closed on any mismatch.

Safety

Fail-closed state machine

A seven-state activation lifecycle separates “the document exists” from “the system is live.” Every arrow is a separate human decision. The first gate, DISTRIBUTED_READY_FENCE, is honestly recorded as UNSATISFIED — so the live path is provably unreachable until a real distributed-fencing primitive is built and validated.

Human authority

Reviewer gate

An independent reviewer role re-derives commit SHAs, PR state, changed files and risky wording from live repository evidence before anything is accepted. Executor reports are treated as claims to verify — no model’s output is ever a source of truth, and the human operator holds final authority.

Architecture

Three refs, three jobs — never conflated.

The design’s core insight is separation: instructions, audit reports and proposed work each get their own surface with their own rules, and none can impersonate another.

The fail-closed lifecycle

Merged is not live. By design.

The recovery projection can only become usable by walking this chain. Every arrow is a separate operator gate; none implies another — and none has been walked as an approval. Merging the contract put its text in the repository, while the projection itself remains PROPOSED and inactive.

PROPOSED_PR_OPENThe contract exists as a reviewable pull request. Authorizes nothing.
LANDED_UNVERIFIEDThe contract text lands in the repository (PR #669 merged to develop, 2026-07-23) — and that is all. Nothing activates by landing.
VALIDATOR_LANDED_INACTIVEA future validator implementation lands — still inactive.
READERSHIP_APPROVEDThe operator approves who may read the projection.
DEDICATED_REF_BOOTSTRAPPED_INACTIVEThe dedicated recovery ref is created — and is still inactive.
ACTIVE_CANONICALThe contract itself is promoted to active policy.
FIRST_GENERATION_ACTIVEOnly here does a consumable recovery snapshot exist at all.

Beneath the lifecycle sits a hard runtime fence: DISTRIBUTED_READY_FENCE must be SATISFIED_VERIFIED before any publication or activation path can execute, and its recorded value is UNSATISFIED — because the Git ref, the canonical assignment and the SharePoint file are three systems with no joint compare-and-swap, and no amount of prose can honestly claim cross-surface freshness. Until a real, separately authorized distributed-fencing primitive exists and is independently validated, every run that reaches this gate terminates BLOCKED with no mutation. The document specifies the machinery and simultaneously proves it is switched off.

Why it matters

Benefits, and honest limits.

What the Vault and its users gain

  • Continuity under failure: once the gated path is walked, a lane that loses its cloud connector can recover bounded read-only continuity instead of stalling the whole operation.
  • A permanent audit trail: every executor report and every sandbox pack becomes a durable, hash-verifiable Git artifact on an append-only ledger that anyone with access can independently re-fetch.
  • Safer parallelism: side-quest work can proceed in sandboxes without ever holding repository authority, so more work happens without weakening the single-writer rule.
  • Trust users can inherit: the same evidence-first discipline that governs AI operations backs the product’s user-facing promises — points ledgers, fairness rules and reward boundaries are governed by the same culture of append-only proof.
  • No silent power creep: nothing in the system can promote itself. Every capability increase is a named, logged human decision.

Limitations, stated plainly

  • This is a documentation and governance implementation only — contracts and state machines, not running code.
  • It landed on develop, not main, and is not operational anywhere.
  • The Git recovery projection is PROPOSED and inactive; OneDrive remains the sole operational canonical surface today.
  • Communication Integrity V2 is landed but inactive; legacy report rules remain operative.
  • DISTRIBUTED_READY_FENCE=UNSATISFIED: the live publication path is deliberately unreachable until a real fencing primitive is separately built, authorized and validated.
  • Every future gate — validator, readership, ref bootstrap, activation, first generation — remains a separate, unpromised operator decision.

Gate

Promote the contract to active policy, then publish the first consumable recovery generation — the earliest moment any lane could actually use it.
